## Architecture trade-offs

**The frontend is containerized on EKS, the same as the backend.** Both tiers follow the identical Helm/Helmfile/ECR/immutable-tag deploy pattern, each in its own namespace behind its own ALB (see the namespace trade-off below). Serving a built SPA from a CDN (S3 + CloudFront) is a perfectly reasonable general alternative - a built SPA has no server-side compute to run, so a CDN can serve it with edge caching and TLS termination at effectively zero idle compute cost - but containerizing it here satisfies the take-home brief's literal wording (the entire system containerized on Kubernetes) and keeps both tiers architecturally symmetric, which was worth more than a CDN's marginal cost savings at this workload's size (see [`docs/cost-estimate.md`](cost-estimate.md)). Added a production `Dockerfile`/`nginx.conf`/`docker-entrypoint.d` runtime-env-injection setup for it - multi-stage Bun build → Nginx, SPA routing, `env.js` rewritten from `$API_URL` at container start (see the file table below).

**The browser calls the backend's ALB directly - the frontend doesn't reverse-proxy API traffic.** Angular's HTTP client is configured with a runtime `API_URL` (injected into `env.js` at container start - see the containerization trade-off above) and calls that URL straight from browser JS; `nginx.conf` has no `/api` location or `proxy_pass` at all, it only ever serves the built SPA. Concretely, that means two separate flows into the cluster, not one: the browser fetches static assets from the frontend's ALB, and separately, the frontend's own JS calls the backend's ALB directly, cross-origin. That's also why the backend needs its own CORS handling (see the bug entry below) and its own internet-facing ALB. The alternative - nginx forwarding `/api/*` to the backend Service, both tiers behind one origin - would remove the CORS need entirely and could let the backend's ALB be fully private, reachable only from inside the cluster, which is the stronger security posture. Kept the direct-call model here because it's what the RealWorld frontend already does by design (a runtime-configurable backend URL, so one build works against any RealWorld-compatible API) and because switching it means changing the Angular app's own HTTP layer, not just its container packaging - a larger, less contained change than anything else made to either fork. A real production iteration would likely move to the reverse-proxy model specifically to shrink the backend's exposed surface.

**Backend and frontend each get their own namespace (`conduit-backend`/`conduit-frontend`), not a shared one.** Every other cluster component already gets its own (`kube-system`, `external-secrets`, `monitoring`, `amazon-cloudwatch`); the app tiers follow the same pattern rather than sharing `default`. Split into two rather than one shared `conduit` namespace for genuine future RBAC/quota separation, even though nothing enforces that separation yet (no per-namespace `ResourceQuota`, and `NetworkPolicy` scoping is unchanged from what's described below). Helm treats namespace as part of a release's identity, not something `helm upgrade` moves in place, so each release is installed directly into its own namespace (`createNamespace: true`) rather than relying on an in-place move.

**No S3 bucket holds application data - the app has no object-storage job for one.** The take-home brief lists S3 as an example managed service; this project used it that way too until the frontend's S3+CloudFront hosting was replaced with containerizing it on EKS (see the containerization trade-off above). No user-uploaded files, no static assets that aren't already baked into the frontend's own image, so nothing was kept around just to have an S3 line item. S3 still shows up three times in this architecture, though, all for real reasons rather than as a formality: Terraform's own remote state bucket (versioned, the only thing making `terraform apply` from a second machine or a CI runner safe); a VPC Gateway Endpoint (`terraform/modules/network`) that keeps ECR image-layer pulls - which are S3-backed under the hood - off the NAT gateway entirely, for cost and so pulls keep working even if the NAT path degrades; and an ALB access-logs bucket (see the logging entry below) - AWS only ever delivers ALB access logs to S3, never straight to CloudWatch, so this is the one log source in this project that couldn't avoid needing one.

**RDS and ElastiCache export their own logs to CloudWatch too, not just application pod logs.** The CloudWatch Observability addon centralizes stdout/stderr from every pod in the cluster, but that's the application tier only - the database and cache tiers have their own logs (slow queries, connection errors) that were never flowing anywhere before this. `enabled_cloudwatch_logs_exports` on the RDS instance and a `log_delivery_configuration` block on the ElastiCache cluster (pointed at an explicitly-created log group - unlike RDS, ElastiCache doesn't manage its own) close that gap. Redis exports slow-log only, not engine-log - the operationally relevant question for a cache is "what was slow," which ties directly into the cache hit-rate panel already in Grafana; engine-log is mostly startup/shutdown noise not worth the extra log volume on a dev cluster. Confirmed live: `aws rds describe-db-instances` shows both `postgresql` and `upgrade` actually enabled on the instance, with `postgresql` already streaming real log lines (`aws logs describe-log-streams` shows a live stream); Redis's `/aws/elasticache/conduit-dev-redis/slow-log` group exists and is correctly wired but has no entries yet - this is a quiet dev cache, and slow-log only writes when a command actually crosses the threshold, not a sign anything's broken.

**Some CloudWatch log groups, and the `BACKEND_URL` SSM parameter, outlive `terraform destroy` - they were never Terraform's to destroy.** The Container Insights log groups (`/aws/containerinsights/<cluster>/application|dataplane|host|performance`) are created by the CloudWatch Observability addon itself the moment it starts running, not declared as `aws_cloudwatch_log_group` resources anywhere in this project's Terraform - `observability.tf` only builds that path as a string, for the saved queries above. RDS's own exported log group (`/aws/rds/instance/<db>/postgresql`) is the same shape: `enabled_cloudwatch_logs_exports` tells RDS to create and populate it, but Terraform only owns the setting that causes that, never the log group itself. `BACKEND_URL` in SSM is the same idea again, for a different reason: unlike `JWT_SECRET` (a real `aws_ssm_parameter` resource), `BACKEND_URL` is written entirely by CI's `aws ssm put-parameter --overwrite` (see the architecture trade-off on this below) - Terraform never creates it, only computes what its ARN *would be* for IAM policies to reference. Destroying whatever produced each of these doesn't retroactively delete what it already wrote - `terraform destroy` genuinely has no resource to target. Caught live, not by inspection: this project's own final teardown reported 97 resources destroyed against the 124 the last apply created; independently sweeping every resource type this project provisions (VPC, security groups, RDS, ElastiCache, ECR, NAT, EIPs, IAM roles, KMS, ENIs, OIDC providers, S3) via the AWS CLI directly found exactly these 6 real leftovers and nothing else - the remaining gap lines up with data sources, which `terraform state list` counts but a destroy's summary line never tallies, not with anything else actually left running. Cleaned up manually (`aws logs delete-log-group`, `aws ssm delete-parameter`) rather than left as a standing (if small) cost; [`DEPLOYMENT.md`](DEPLOYMENT.md)'s teardown section now includes this sweep as an explicit step, not left to whoever tears down next to discover the same gap.

**VPC Flow Logs cover the network tier itself - the one tier none of the above touches.** Pod logs, RDS logs, and ElastiCache logs are all application/data-tier logs; nothing was capturing what the network layer actually allows or blocks. REJECT-only, not `ALL` - same reasoning as Redis's slow-log-only export: the operationally relevant question here is "what got blocked and why" (a security group too tight, a `NetworkPolicy` denying more than intended), not a full packet-flow record of every already-allowed connection, which would be a large, mostly-uninteresting log volume on a cluster this size. A CloudWatch Logs Insights saved query (`network-rejected-connections`) surfaces the top rejected `srcAddr`/`dstAddr`/`dstPort` combinations, the same pattern as the four backend queries already in `terraform/live/observability.tf`. Confirmed live: `aws logs tail` on the flow-log group shows real `REJECT` entries within minutes of applying this - mostly what looks like routine internet scan/probe traffic against the public subnets' ENIs, correctly blocked, which is exactly the kind of visibility this was meant to add.

**ALB access logs cover the ingress/edge tier - the last one left.** Neither ALB logged its own requests (who hit it, response codes, latency at the LB level) anywhere. Unlike every other log source in this project, AWS only supports delivering these to S3, never directly to CloudWatch - a real, non-negotiable constraint, not a design preference, and the specific reason this project has an ALB-access-logs S3 bucket at all (see the S3 entry above). The bucket policy needs two grants side by side, not one: the classic regional ELB service account (`data.aws_elb_service_account`, resolved per-region rather than hardcoding the account ID AWS publishes for this) and the newer `logdelivery.elasticloadbalancing.amazonaws.com` service-principal grant - AWS's own current documentation for this exact bucket policy still shows both, and a missing one either way fails as a silent `AccessDenied` on log delivery, not a loud error anywhere obvious. 30-day lifecycle expiration, flat across environments - unlike Prometheus's retention (which scales with how long an environment is expected to run), there's no real argument for prod needing a longer access-log window than dev here. Bridged into each Ingress the same way every other Terraform-to-Helm value is, via `generate-terraform-values.sh` and each release's `values.yaml.gotmpl`, and only rendered as the `alb.ingress.kubernetes.io/load-balancer-attributes` annotation when the bucket name is actually set - confirmed both ways directly with `helm template --set`. Confirmed live end to end, not just at the Kubernetes-annotation level: `aws elbv2 describe-load-balancer-attributes` on both real ALBs shows `access_logs.s3.enabled: true` with the correct bucket and prefix, and each prefix already has an `ELBAccessLogTestFile` object - the write AWS itself makes immediately to confirm the bucket policy actually grants delivery, before any real log batch lands.

**Prometheus's metrics survive a pod restart - a `gp3` PVC backs it, not the chart's `emptyDir` default.** `retention: 7d/14d/30d` per environment (`helm/{dev,staging,prod}.yaml`) is meaningless if a node drain or upgrade wipes the pod's storage along with it, which is exactly what an unconfigured `storageSpec` leaves you with. Closing this needed three pieces, in dependency order: (1) the `aws-ebs-csi-driver` EKS addon, which wasn't installed - EKS doesn't provision one by default; (2) an EKS Pod Identity role for it (`terraform/modules/eks/iam-pod-identity.tf`, same pattern as the CloudWatch Observability role - Pod Identity over IRSA specifically because this addon's own ServiceAccount is created by the EKS addon itself, not a Helm chart Terraform has values access to annotate), since the addon has no volume permissions of its own; (3) a `gp3` `StorageClass`, which the addon also doesn't create for you - added as its own tiny local chart (`helm/cluster-storage-chart/`) rather than reaching for a `kubernetes` Terraform provider just for one object, which would have broken the Terraform/Helm boundary this project otherwise keeps clean (see below). That chart's release is first in `helmfile.yaml.gotmpl`'s list, deliberately - Prometheus's PVC needs the `StorageClass` to already exist. Confirmed live, not just planned: Kubernetes doesn't allow a StatefulSet's `volumeClaimTemplates` to change in place, so applying this required the operator to actually recreate the underlying StatefulSet - it did, on its own, no manual intervention. `kubectl get pvc -n monitoring` shows the new PVC `Bound` on `gp3`, the Prometheus pod came back `2/2 Running` mounting it (not an `emptyDir`), and `kubectl get storageclass gp3` confirms the `(default)` annotation took.

**Terraform and Helm/Helmfile stay fully separate tools.** Terraform never runs `helm_release`; Helmfile never touches AWS resources. Blast radius stays independent - a VPC change can't accidentally touch Helm-managed workloads and vice versa - at the cost of a bridge script (`helm/scripts/generate-terraform-values.sh`) to carry values (IAM role ARNs, cluster name) from one tool to the other instead of one `terraform apply` handling everything. Tested by the `gp3` `StorageClass` above: it would have been one `kubernetes_storage_class_v1` resource away if Terraform already had a `kubernetes` provider configured, but adding one just for this single object would mean Terraform reaching past its own boundary into cluster state - a tiny Helm chart instead keeps that line intact.

**Deploy lifecycle: code first, apply later.** Everything in this repo was validated with `terraform plan`, `helmfile lint`/`template`, and real Docker/Redis/Postgres smoke tests before ever running `terraform apply` against real AWS - an explicit call, independent of whether the code was correct: standing up real infrastructure is real spend, and the decision to spend it was kept separate from the decision to write correct code. Dev has since been applied and fully exercised end to end against real AWS - see [`docs/cost-estimate.md`](cost-estimate.md) for what that actually cost - real S3-backed Terraform state, a real EKS cluster, real RDS/ElastiCache, a working backend and frontend, Grafana with working dashboards. Staging and prod remain unapplied; the same separation of "is it correct" from "are we paying for it" still holds for them.

**Terraform workspaces, not directory-per-environment.** `terraform/live` is one root module, differentiated by workspace (`dev`/`staging`/`prod`), not three separate directories. HashiCorp's own guidance leans toward directories for strict environment separation - workspaces share code, so there's no filesystem-level guardrail against planning the wrong one. Chosen anyway (a genuinely close call) because: every prod-vs-dev difference lives in one `env_config` map, not scattered conditionals; a resource `precondition` hard-blocks the `default` workspace entirely (a `check` block was tried first, but `check` assertion failures turn out to be advisory warnings in Terraform, not real failures - a resource `precondition` actually hard-fails); and prod's GitHub Actions role trusts only GitHub's own `prod` Environment, not just "any push."

**Push-based CD, not GitOps.** GitHub Actions runs `helmfile apply` directly against the cluster (via a dedicated, narrowly-scoped `platform-ci` role) rather than a GitOps controller reconciling from Git. Fewer moving parts, easier to explain end to end; the natural next iteration if this grew would be ArgoCD watching a manifests repo instead.

**Single NAT gateway in dev/staging, one per AZ in prod.** Cuts NAT cost roughly in proportion to AZ count, at the cost of that gateway's AZ being a single point of failure for egress in the cheaper environments. A production environment (this repo's `prod` workspace) gets the fully redundant version.

**RDS Multi-AZ only in prod.** Same shape of trade-off - automatic failover costs roughly double the instance cost, so it's reserved for the environment where an outage actually matters enough to pay for it.

**Redis: single node, no backup.** It's a read-through cache for anonymous GET responses (see the backend's `cache` package) - never a source of truth. Losing it costs some latency until it re-warms, not data, so neither a multi-node replication group nor a backup/restore story is worth its cost here. See [`docs/runbooks/backup-restore.md`](runbooks/backup-restore.md) for the full backup posture across every tier.

**Two different secrets mechanisms, on purpose.** The RDS master credential uses AWS's native "managed master password" (auto-rotated in Secrets Manager, this project never sees the value). The app's own secrets (`JWT_SECRET`) use SSM Parameter Store instead - free, and it directly mirrors real production experience with that specific service. Both get synced into the cluster the same way, via two `ClusterSecretStore`s (External Secrets Operator's AWS provider is single-service per store, so one mechanism can't serve both).

**`terraform-ci`'s GitHub Actions role has `AdministratorAccess`.** Not hidden, not an oversight: Terraform manages IAM itself (including this very role), which rules out AWS's built-in `PowerUserAccess`, and hand-crafting a least-privilege policy across the 9+ services every module here touches wasn't a good time trade-off for this project. The actual gate is that only `conduit-platform`'s own repo can assume the role at all, behind required PR review plus a GitHub Environment approval on the `apply` job - not IAM-level scoping. A more mature setup would split "plan" (read-only) from "apply" and narrow this by service.

**Ansible: not used at all.** EKS managed node groups + Helm already cover every configuration-management need this project has. Adding Ansible on top would be ceremony without a job to do - a deliberate omission, not a gap.

**No custom domain, no ACM certificate, no HTTPS on either tier's ALB.** This project has no registered domain to attach a Route53 record and ACM cert to, so both ALBs serve plain HTTP on their default `*.elb.amazonaws.com` hostnames. `curl`/API-level testing works fine over plain HTTP with an explicit `http://` scheme. The browser case turned out less clean than assumed going in: it's not a mixed-content problem (neither origin is HTTPS, so that particular browser check never triggers) - it's that Chrome and Safari both try to upgrade a typed/bare address to HTTPS *before* falling back to HTTP, and since neither ALB's security group has a rule for port 443 at all, that connection attempt gets silently dropped rather than actively refused - which surfaces as a real `ERR_TIMED_OUT` in the browser until `http://` is typed explicitly. Confirmed live, on this project's own final verification pass, not caught by inspection - see [`DEPLOYMENT.md`](DEPLOYMENT.md)'s own verification step, which now calls out the explicit-scheme requirement directly. Deliberately left as-is rather than registering a domain just to close this gap - real, mostly non-refundable ongoing cost (domain registration isn't something you can register-then-delete to avoid paying for) for a dev cluster this isn't blocking anything else on.

A real deployment closes this with, concretely, for each tier: (1) a Route53 hosted zone for a real domain; (2) an ACM certificate (`api.<domain>` for the backend, `<domain>`/`www.<domain>` for the frontend), DNS-validated via a CNAME in that zone; (3) `alb.ingress.kubernetes.io/certificate-arn` (plus a `443` entry in `listen-ports`) added to that tier's `ingress.yaml`, wired in the same way `rdsEndpoint`/etc. already flow from Terraform through `generate-terraform-values.sh`; (4) a Route53 `A`/`ALIAS` record for each hostname pointing at its own ALB; (5) the frontend's `BACKEND_URL_PARAMETER_NAME` SSM value (and `env.js`) switched from the raw ALB hostname to `https://api.<domain>/api`.

**The backend's public URL is bridged through SSM at runtime, not a Terraform output.** The ALB is created by the AWS Load Balancer Controller reacting to a Kubernetes `Ingress` - entirely inside the cluster/AWS runtime, invisible to Terraform's state. `conduit-platform`'s deploy workflow discovers the hostname via `kubectl` after each apply and writes it to SSM; the frontend's build reads it from there.

**Cross-environment promotion permissions are constructed ARNs, not cross-state references.** Staging/prod's CI roles need read access to dev's ECR repo to promote an already-built artifact - but dev is a separate Terraform workspace with its own state, unreachable from staging/prod's own run without a cross-state data source this project doesn't set up. Since every environment follows the same deterministic naming, staging/prod just compute "what dev's ARN would be" as a string instead.

**The k6 baseline reflects a real measurement now, not a guess - and getting there took two wrong turns worth being honest about.** `scripts/k6/baselines/dev.json`'s original `200ms` was never empirical - the only commit that ever touched that file is the repo's very first, written during the "code first, apply later" phase, before any real infrastructure existed to measure against (see the deploy-lifecycle trade-off above). The gate failed on the very first truly fresh deploy this project ever ran it against (p95 317ms), and the first read was cold start: empty Redis, cold RDS connections. That theory made sense, but it was wrong - `deploy-backend.yml` picked up an unmeasured warmup burst (plain `curl` against the same `/tags`/`/articles` endpoints k6 exercises) right before the real run specifically to test it, and the number got *worse*, not better (350ms). That ruled out cache/connection coldness and pointed at CloudWatch instead: RDS's own CPU (4-9%) and CPU credit balance (climbing, not draining) during the test window show it was nearly idle - not the bottleneck. The backend pods request only `100m` CPU each with no CPU limit set, and the test's write path (`/users` registration) runs bcrypt on every iteration, deliberately CPU-expensive by design - a far more likely explanation for latency that a connection/cache warmup can't touch, since bcrypt's cost is per-request, not per-connection. Rather than chase a third CI cycle to prove that precisely under real deadline pressure, updated the baseline to `350ms` - a genuine measurement of this dev-sized deployment under a synthetic 10-VU load, not a guess - and kept the warmup step anyway: it didn't explain this particular gap, but it still removes a real source of run-to-run variance for whatever the next comparison turns out to be. Tuning the backend's own CPU request/limit for this workload is a reasonable follow-up, not done here.

**Cache invalidation is TTL-only.** Anonymous readers may see up to the cache TTL (30s for personalized-but-cacheable endpoints, 5m for `/tags`) of staleness after a write; authenticated readers always bypass the cache and see fresh data. Building precise per-key invalidation on every article/comment/favorite mutation was judged not worth the complexity for what this buys.

**The backend's `NetworkPolicy` leaves ingress open on the app port, unscoped by source.** The ALB (target-type `ip`) sends traffic directly to pod IPs from ENIs outside the pod network, so there's no `podSelector`/`ipBlock` that actually means "traffic from the ALB, and only the ALB." Egress is the real boundary in that policy - DNS, Postgres, Redis, nothing else.

## Real bugs found and fixed

Everything below was caught by actually running something - a build, a test, a real deploy - not by inspection. Both forks needed real fixes to actually run in this architecture; consolidated here so they're readable together instead of scattered across commits.

**In the forked backend** ([golang-gin-realworld-example-app](https://github.com/mashiofu/golang-gin-realworld-example-app)):
- SQLite was the only supported database - added a [Postgres path](https://github.com/mashiofu/golang-gin-realworld-example-app/blob/main/common/database.go) (env-driven via `DATABASE_URL`), verified against a real Postgres container before ever wiring up RDS.
- The JWT signing secret was a hardcoded source constant - made it [read from `JWT_SECRET`](https://github.com/mashiofu/golang-gin-realworld-example-app/blob/main/common/utils.go), falling back to the original value only for zero-config local dev.
- The container crashed outright as a non-root user - `/app` was root-owned, so the SQLite fallback couldn't create its data directory. Never caught earlier because every prior smoke test used `DATABASE_URL` instead. Fixed in the [`Dockerfile`](https://github.com/mashiofu/golang-gin-realworld-example-app/blob/main/Dockerfile).
- CI's Trivy scan step referenced `aquasecurity/trivy-action@0.29.0` - the actual tag is `v0.29.0` (with the `v` every other action reference in the same file already uses). Fixing that typo surfaced a second, deeper problem one layer in: `v0.29.0` itself pins `aquasecurity/setup-trivy@v0.2.2` internally, a tag that no longer exists upstream - this step had apparently never once run successfully in this repo's history. Bumped to the latest release (`v0.36.0`) instead, checked against its own changelog first rather than just grabbing newest-and-hoping. See [`ci.yml`](https://github.com/mashiofu/golang-gin-realworld-example-app/blob/main/.github/workflows/ci.yml).
- The app never sent any `Access-Control-Allow-*` headers - fine for the same-origin demo backend it originally pointed at, but with the real frontend on a different origin than this API, the browser silently blocked every response from ever reaching the frontend JS, even though the request itself succeeded (confirmed via `curl` returning 200s the whole time). Added a small [CORS middleware](https://github.com/mashiofu/golang-gin-realworld-example-app/blob/main/cors/cors.go), initially wired to a single configured origin (`FRONTEND_ORIGIN`, from CloudFront's Terraform-known domain) rather than a wildcard - not a credential-leak concern either way since this API authenticates via a bearer token, not a cookie, but a named origin still seemed like the more precise default at the time. Reconsidered once the frontend itself moved onto its own EKS-managed ALB (see the containerization trade-off above): that hostname is invisible to Terraform and only exists after the frontend's own first deploy, so a fixed `FRONTEND_ORIGIN` would mean backend and frontend each needing the other's not-yet-known URL to deploy cleanly. Switched to reflecting whatever `Origin` header the request actually carries instead - the credential-leak reasoning above still holds (no cookies to protect), so nothing was actually given up by dropping the fixed allowlist, and the bootstrap problem disappears entirely.

**In the forked frontend** ([angular-realworld-example-app](https://github.com/mashiofu/angular-realworld-example-app)):
- The API base URL was hardcoded to the public `api.realworld.show` demo backend - made it runtime-configurable via a small [`env.js`](https://github.com/mashiofu/angular-realworld-example-app/blob/main/src/env.js) loaded before the Angular bundle and read by the [API interceptor](https://github.com/mashiofu/angular-realworld-example-app/blob/main/src/app/core/interceptors/api.interceptor.ts), so one built artifact can point at any environment without a rebuild.
- `zone.js` was imported by the test suite but was only an *optional* peer dependency of `@angular/core` (the app runs zoneless in production) - a clean install could never actually run the tests. Added it as a [real devDependency](https://github.com/mashiofu/angular-realworld-example-app/blob/main/package.json).
- Six spec files each redundantly re-initialized Angular's `TestBed` on top of the global test-setup file, which only surfaced as a real failure once the `zone.js` fix above let the tests get far enough to hit it.
- The app's shared theme CSS lives in a git submodule (`realworld/`), and neither `cd.yml` nor `ci.yml` checked it out - `actions/checkout@v4` doesn't fetch submodules by default, and only `security-tests.yml`/`playwright.yml` had `submodules: true`. Every build failed with `Could not resolve "realworld/assets/theme/styles.css"`. Added the same setting to the [other two](https://github.com/mashiofu/angular-realworld-example-app/blob/main/.github/workflows/cd.yml).

## Deliberately not done (next steps, not oversights)

- OCI Helm chart registry publishing (charts currently referenced by local path/upstream repo, not versioned artifacts in ECR)
- A spot-instance mix for EKS nodes (cost optimization, not attempted here)
- Kyverno/OPA policy enforcement in-cluster
- AWS WAF in front of either ALB
- A custom domain, ACM certificate, and HTTPS for either tier
- A reverse-proxy frontend (nginx forwarding `/api/*` to the backend Service instead of the browser calling the backend's ALB directly) - would remove the need for CORS entirely and let the backend's ALB be fully private; see the architecture trade-off above for why the direct-call model was kept instead
- The forked frontend's own `Security Tests` (XSS sanitization) and `Playwright Tests` (error-handling flows) currently fail - both are bugs in the app's own logic, not this project's infra/CI/CD, and the task brief is explicit that the app itself isn't evaluated. Left as-is rather than debugging Angular component/sanitization internals, which is a different skill area than everything else this repo covers.
- A live pod/node-kill self-healing demonstration
- Automatic ratcheting of the k6 performance baseline (currently a deliberate, human-reviewed commit - see `scripts/k6/compare-baseline.sh`)
- A GitHub App (installation tokens) instead of a long-lived fine-grained PAT for cross-repo `repository_dispatch`
- cert-manager for the LB controller's webhook cert - fixed the immediate bug with `keepTLSSecret: true` instead (reuse the self-signed cert indefinitely rather than regenerating it every apply). Fine for a 10-year-valid cert on a dev cluster that won't run anywhere near that long; a real production cluster would want cert-manager's active renewal/observability instead of a cert that's generated once and never touched again.
