# Design Decisions & Trade-offs

Every one of these is referenced from a code comment near where it actually matters - this page exists so they're readable together, not scattered. Organized in three parts: deliberate architectural trade-offs, real bugs this project found and fixed (mostly in the forked apps, a few in this platform's own code), and what's knowingly left undone.

## Architecture trade-offs

**The frontend is containerized on EKS, the same as the backend - this replaced an earlier S3/CloudFront static-hosting design.** The take-home brief calls for the entire system containerized on Kubernetes; the initial design instead served the frontend as a static Angular build from S3 via CloudFront, on the reasoning that a built SPA has no server-side compute to run, so putting it behind an Ingress on EKS would mean paying for and managing pods that just serve static files a CDN already does better (edge caching, TLS termination, zero idle compute cost). Reconsidered to actually satisfy the brief's literal wording and for architectural symmetry with the backend: the forked frontend repo already shipped a production-ready `Dockerfile`/`nginx.conf`/`docker-entrypoint.d` runtime-env-injection setup that had simply never been wired into CI/CD, so containerizing it meant reusing existing assets, not building new ones. The frontend now follows the identical Helm/Helmfile/ECR/immutable-tag pattern as the backend, in its own namespace behind its own ALB (see the namespace trade-off below). Net effect on cost is a real increase, not a wash - a second ALB replaced S3+CloudFront, and a static-asset CDN was genuinely cheaper (see `docs/cost-estimate.md`) - accepted anyway because per-tier consistency and the brief's literal requirement outweighed the marginal savings at this workload's size.

**Backend and frontend each get their own namespace (`conduit-backend`/`conduit-frontend`), not a shared one.** Both originally landed in bare `default` - every other cluster component already gets its own (`kube-system`, `external-secrets`, `monitoring`, `amazon-cloudwatch`), so sharing `default` was the actual inconsistency, independent of whether backend and frontend would otherwise have shared one namespace together. Split into two rather than one shared `conduit` namespace for genuine future RBAC/quota separation, even though nothing enforces that separation yet (no per-namespace `ResourceQuota`, and `NetworkPolicy` scoping is unchanged from what's described below). Helm treats namespace as part of a release's identity, not something `helm upgrade` moves in place, so this was a real uninstall-from-`default`/reinstall-into-new-namespace migration, done live through the actual CI/CD pipeline rather than just a values change.

**Deploy lifecycle: code first, apply later.** Everything in this repo was validated with `terraform plan`, `helmfile lint`/`template`, and real Docker/Redis/Postgres smoke tests before ever running `terraform apply` against real AWS - an explicit call, independent of whether the code was correct: standing up real infrastructure is real spend, and the decision to spend it was kept separate from the decision to write correct code. Dev has since been applied and fully exercised end to end against real AWS - see `docs/cost-estimate.md` for what that actually cost - real S3-backed Terraform state, a real EKS cluster, real RDS/ElastiCache, a working backend and frontend, Grafana with working dashboards. Staging and prod remain unapplied; the same separation of "is it correct" from "are we paying for it" still holds for them.

**Terraform workspaces, not directory-per-environment.** `terraform/live` is one root module, differentiated by workspace (`dev`/`staging`/`prod`), not three separate directories. HashiCorp's own guidance leans toward directories for strict environment separation - workspaces share code, so there's no filesystem-level guardrail against planning the wrong one. Chosen anyway (a genuinely close call) because: every prod-vs-dev difference lives in one `env_config` map, not scattered conditionals; a resource `precondition` hard-blocks the `default` workspace entirely (a `check` block was tried first and turned out to be advisory-only - see the bug list below); and prod's GitHub Actions role trusts only GitHub's own `prod` Environment, not just "any push."

**Terraform and Helm/Helmfile stay fully separate tools.** Terraform never runs `helm_release`; Helmfile never touches AWS resources. Blast radius stays independent - a VPC change can't accidentally touch Helm-managed workloads and vice versa - at the cost of a bridge script (`helm/scripts/generate-terraform-values.sh`) to carry values (IAM role ARNs, cluster name) from one tool to the other instead of one `terraform apply` handling everything.

**Push-based CD, not GitOps.** GitHub Actions runs `helmfile apply` directly against the cluster (via a dedicated, narrowly-scoped `platform-ci` role) rather than a GitOps controller reconciling from Git. Fewer moving parts, easier to explain end to end; the natural next iteration if this grew would be ArgoCD watching a manifests repo instead.

**Single NAT gateway in dev/staging, one per AZ in prod.** Cuts NAT cost roughly in proportion to AZ count, at the cost of that gateway's AZ being a single point of failure for egress in the cheaper environments. A production environment (this repo's `prod` workspace) gets the fully redundant version.

**RDS Multi-AZ only in prod.** Same shape of trade-off - automatic failover costs roughly double the instance cost, so it's reserved for the environment where an outage actually matters enough to pay for it.

**Redis: single node, no backup.** It's a read-through cache for anonymous GET responses (see the backend's `cache` package) - never a source of truth. Losing it costs some latency until it re-warms, not data, so neither a multi-node replication group nor a backup/restore story is worth its cost here. See `docs/runbooks/backup-restore.md` for the full backup posture across every tier.

**Two different secrets mechanisms, on purpose.** The RDS master credential uses AWS's native "managed master password" (auto-rotated in Secrets Manager, this project never sees the value). The app's own secrets (`JWT_SECRET`) use SSM Parameter Store instead - free, and it directly mirrors real production experience with that specific service. Both get synced into the cluster the same way, via two `ClusterSecretStore`s (External Secrets Operator's AWS provider is single-service per store, so one mechanism can't serve both).

**`terraform-ci`'s GitHub Actions role has `AdministratorAccess`.** Not hidden, not an oversight: Terraform manages IAM itself (including this very role), which rules out AWS's built-in `PowerUserAccess`, and hand-crafting a least-privilege policy across the 9+ services every module here touches wasn't a good time trade-off for this project. The actual gate is that only `conduit-platform`'s own repo can assume the role at all, behind required PR review plus a GitHub Environment approval on the `apply` job - not IAM-level scoping. A more mature setup would split "plan" (read-only) from "apply" and narrow this by service.

**Ansible: not used at all.** EKS managed node groups + Helm already cover every configuration-management need this project has. Adding Ansible on top would be ceremony without a job to do - a deliberate omission, not a gap.

**No custom domain, no ACM certificate, no HTTPS on either tier's ALB.** This project has no registered domain to attach a Route53 record and ACM cert to, so both ALBs serve plain HTTP on their default `*.elb.amazonaws.com` hostnames. Confirmed live, not just theoretical, back when the frontend was still served from CloudFront (HTTPS) and the backend was HTTP-only: Chrome's mixed-content auto-upgrade silently promoted the frontend's API calls to HTTPS, which then hung forever against an ALB with no TLS listener at all - the app loaded but never got past "Loading articles...". That specific failure mode is gone now that the frontend is also a plain-HTTP ALB (see the containerization trade-off above) - both tiers are consistently HTTP, so there's no mismatch left to trigger the auto-upgrade - but the underlying gap, no TLS anywhere, is unchanged. `curl`/API-level testing was unaffected either way, then and now. Deliberately left as-is rather than registering a domain just to close this gap - real, mostly non-refundable ongoing cost (domain registration isn't something you can register-then-delete to avoid paying for) for a dev cluster this isn't blocking anything else on.

A real deployment closes this with, concretely, for each tier: (1) a Route53 hosted zone for a real domain; (2) an ACM certificate (`api.<domain>` for the backend, `<domain>`/`www.<domain>` for the frontend), DNS-validated via a CNAME in that zone; (3) `alb.ingress.kubernetes.io/certificate-arn` (plus a `443` entry in `listen-ports`) added to that tier's `ingress.yaml`, wired in the same way `rdsEndpoint`/etc. already flow from Terraform through `generate-terraform-values.sh`; (4) a Route53 `A`/`ALIAS` record for each hostname pointing at its own ALB; (5) the frontend's `BACKEND_URL_PARAMETER_NAME` SSM value (and `env.js`) switched from the raw ALB hostname to `https://api.<domain>/api`.

**The backend's public URL is bridged through SSM at runtime, not a Terraform output.** The ALB is created by the AWS Load Balancer Controller reacting to a Kubernetes `Ingress` - entirely inside the cluster/AWS runtime, invisible to Terraform's state. `conduit-platform`'s deploy workflow discovers the hostname via `kubectl` after each apply and writes it to SSM; the frontend's build reads it from there.

**Cross-environment promotion permissions are constructed ARNs, not cross-state references.** Staging/prod's CI roles need read access to dev's ECR repo/S3 bucket to promote an already-built artifact - but dev is a separate Terraform workspace with its own state, unreachable from staging/prod's own run without a cross-state data source this project doesn't set up. Since every environment follows the same deterministic naming, staging/prod just compute "what dev's ARN would be" as a string instead.

**Cache invalidation is TTL-only.** Anonymous readers may see up to the cache TTL (30s for personalized-but-cacheable endpoints, 5m for `/tags`) of staleness after a write; authenticated readers always bypass the cache and see fresh data. Building precise per-key invalidation on every article/comment/favorite mutation was judged not worth the complexity for what this buys.

**The backend's `NetworkPolicy` leaves ingress open on the app port, unscoped by source.** The ALB (target-type `ip`) sends traffic directly to pod IPs from ENIs outside the pod network, so there's no `podSelector`/`ipBlock` that actually means "traffic from the ALB, and only the ALB." Egress is the real boundary in that policy - DNS, Postgres, Redis, nothing else.

## Real bugs found and fixed

Everything below was caught by actually running something - a build, a test, a `terraform plan`, a `helmfile template` - not by inspection. Consolidated here because the pattern itself is a finding: adapting a demo app (or writing new infra) surfaces real, specific gaps regardless of how careful the initial pass is; the point is catching them before they ship, not never introducing them.

**In the forked backend:**
- SQLite was the only supported database - added a Postgres path (env-driven via `DATABASE_URL`), verified against a real Postgres container before ever wiring up RDS.
- The JWT signing secret was a hardcoded source constant - made it read from `JWT_SECRET`, falling back to the original value only for zero-config local dev.
- The container crashed outright as a non-root user - `/app` was root-owned, so the SQLite fallback couldn't create its data directory. Never caught earlier because every prior smoke test used `DATABASE_URL` instead.
- CI's Trivy scan step referenced `aquasecurity/trivy-action@0.29.0` - the actual tag is `v0.29.0` (with the `v` every other action reference in the same file already uses). A typo, not a version choice to reconsider.
- The app never sent any `Access-Control-Allow-*` headers - fine for the same-origin demo backend it originally pointed at, but with the real frontend on a different origin than this API, the browser silently blocked every response from ever reaching the frontend JS, even though the request itself succeeded (confirmed via `curl` returning 200s the whole time). Added a small CORS middleware, initially wired to a single configured origin (`FRONTEND_ORIGIN`, from CloudFront's Terraform-known domain) rather than a wildcard - not a credential-leak concern either way since this API authenticates via a bearer token, not a cookie, but a named origin still seemed like the more precise default at the time. Reconsidered once the frontend itself moved onto its own EKS-managed ALB (see the containerization trade-off above): that hostname is invisible to Terraform and only exists after the frontend's own first deploy, so a fixed `FRONTEND_ORIGIN` would mean backend and frontend each needing the other's not-yet-known URL to deploy cleanly. Switched to reflecting whatever `Origin` header the request actually carries instead - the credential-leak reasoning above still holds (no cookies to protect), so nothing was actually given up by dropping the fixed allowlist, and the bootstrap problem disappears entirely.

**In the forked frontend:**
- The API base URL was hardcoded to the public `api.realworld.show` demo backend - made it runtime-configurable via a small `env.js` loaded before the Angular bundle, so one built artifact can point at any environment without a rebuild.
- `zone.js` was imported by the test suite but was only an *optional* peer dependency of `@angular/core` (the app runs zoneless in production) - a clean install could never actually run the tests. Added it as a real devDependency.
- Six spec files each redundantly re-initialized Angular's `TestBed` on top of the global test-setup file, which only surfaced as a real failure once the `zone.js` fix above let the tests get far enough to hit it.
- The app's shared theme CSS lives in a git submodule (`realworld/`), and neither `cd.yml` nor `ci.yml` checked it out - `actions/checkout@v4` doesn't fetch submodules by default, and only `security-tests.yml`/`playwright.yml` had `submodules: true`. Every build failed with `Could not resolve "realworld/assets/theme/styles.css"`. Added the same setting to the other two.

**In this platform's own code:**
- A circular Terraform module dependency (the `eks` module wanted RDS's secret ARN; RDS wanted `eks`'s security group ID) - resolved by having the IAM policy scope by RDS's own secret-naming convention instead of the exact ARN.
- `for_each` over a list built from an apply-time-unknown value (the cluster security group ID) - Terraform correctly rejects this since the key set becomes unknown; fixed the standard way, switching to a map with a static key.
- A `check` block was the first attempt at hard-blocking the `default` Terraform workspace - only to discover `check` assertion failures are advisory warnings in Terraform, not real failures. Replaced with a resource `precondition`, which does hard-fail, wired via explicit `depends_on` into every module.
- Three separate `{{ }}` escaping bugs, all the same root cause: Helm and another tool (External Secrets Operator, Prometheus Alertmanager, Grafana) both use Go template `{{ }}` syntax, and Helm happily "resolves" the other tool's placeholders unless they're deliberately escaped. Caught each time by actually running `helmfile template` and reading the parse error, not by inspection.
- A naming mismatch (the GitHub Environment was `"production"`, the Terraform workspace is `"prod"`) - same concept, two names, fixed before it propagated into every CI workflow.
- Promotion workflows would have failed silently: staging/prod's CI roles only had permissions on their *own* ECR repo/S3 bucket, not dev's, and promotion needs to read dev's.
- The forked frontend repo shipped its own `deploy.yml`, firing on every push to `main` and creating a GitHub Release - directly conflicting with this project's own `cd.yml` on the identical trigger. Removed.
- `helmfile apply` raced its own platform add-ons: the AWS Load Balancer Controller's cluster-wide `Service`-mutating webhook is registered as soon as its chart's objects exist, but the pod backing it takes longer to actually go `Ready`. Without `--wait`, Helmfile moved on to `external-secrets` (which also creates a `Service`) before the webhook had any endpoints, failing with `no endpoints available for service aws-load-balancer-webhook-service`. Fixed by adding `wait: true` to every add-on release, not just the one caught live - `external-secrets` runs the identical hazard for the `backend` release's `ExternalSecret` later in the same list, just not hit yet.
- A second race in the same area, hit immediately after fixing the first: `x509: certificate signed by unknown authority ... aws-load-balancer-controller-ca` on a subsequent release's `Service` creation. First read as a narrow, self-healing timing window (both controller replicas showed matching cert/caBundle fingerprints by the time it was checked) and documented as a retry-on-sight transient - wrong call, corrected once it recurred ~9 minutes later and took out an entire release (kube-prometheus-stack, all 11 `Service` objects, both replicas) on the very next apply. That recurrence is what made it worth reading the actual chart source rather than trusting the first, more charitable read: `templates/_helpers.tpl`'s `webhookCerts` helper calls `genCA`/`genSignedCert` **unconditionally** unless `keepTLSSecret: true` is set and a prior Secret already exists via `lookup` - so every `helm upgrade --install` of this release, even one with zero changes on our side, mints a brand-new random self-signed CA/cert and repatches the webhook's caBundle. The 2 replicas then reload that new cert off their mounted Secret volume independently (~10s poll each, not synchronized), so any webhook-intercepted object created cluster-wide in that gap fails the same way - and since the regenerated Secret content means `helm-diff` never sees this release as unchanged, it was recurring on every single apply, not occasionally. Fixed with one line, `keepTLSSecret: true` - the chart's own supported way to reuse the existing cert on upgrade instead of regenerating it (a fresh one still gets generated on the genuine first install, when `lookup` finds nothing yet).
- All four GitHub Actions CI roles (`iam-github-actions-role` module - backend-ci, frontend-ci, platform-ci, terraform-ci) failed `AssumeRoleWithWebIdentity` with `Not authorized`, despite a correctly-configured OIDC provider (right audience, standard thumbprint) and a trust policy that looked like it should already match. Root cause was external, not this project's own bug: GitHub shipped ["immutable subject claims"](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens/) for OIDC tokens on 2026-04-23 - every repo created after 2026-07-15 uses the new format automatically, no opt-out, and every repo here was created well after that date. The `sub` claim became `repo:OWNER@OWNER-ID/REPO@REPO-ID:...` instead of the classic `repo:OWNER/REPO:...` this module's pattern (and virtually every existing tutorial) assumed. Found by pulling the actual failed `AssumeRoleWithWebIdentity` call from CloudTrail's default event history instead of continuing to guess from the trust policy alone - its real `userIdentity.principalId` showed the new format directly. Fixed by widening each trust policy's `sub` pattern to `repo:${org}@*/${repo}@*:...`: `@` can't appear in a GitHub username or repo name, so the wildcard only ever matches the numeric ID GitHub inserts there, not a different org or repo.
- Every conduit-platform CI workflow that touches Terraform state (`terraform.yml`'s `plan`/`apply` jobs, `deploy-backend.yml`) was silently operating against an empty local backend instead of the real one - discovered while chasing the OIDC fix above, once credentials started working and a *different* error appeared (`Workspace "dev" doesn't exist`). Two compounding causes, not one: (1) `terraform/live/versions.tf`'s `backend "s3" {}` block - the actual fix for the ambiguity documented earlier in this list - had been sitting locally modified for a while but never actually committed and pushed, so every fresh checkout (CI included) still had the block fully commented out; (2) even with that block active, neither workflow's `terraform init` passed `-backend-config`, and `backend.hcl` (the local source of those values) is gitignored by design, so CI had no way to reach the real bucket regardless. Confirmed by reproducing the exact CI init command against an isolated fresh clone: `terraform workspace list` showed only `default` until both fixes were applied together, `default` **and** `dev` afterward. Fixed by committing the pending `versions.tf` change, adding a `TF_STATE_BUCKET` repo variable to `scripts/sync-github-environments.sh` (read from `backend.hcl`, the same file a local run already uses for this exact value), and passing it plus the project's fixed `key`/`use_lockfile` conventions as `-backend-config` flags in both workflows' `terraform init` steps.
- `deploy-backend.yml` installs its own `helm`/`helmfile` from scratch rather than relying on a pre-installed image, and that install had never actually been exercised until the fix above got far enough to reach it. Two version problems back to back: first, no `helm-diff` plugin at all (`unknown command "diff" for "helm"` - the same plugin-not-built-in gap `docs/DEPLOYMENT.md`'s Prerequisites table documents locally, just not yet applied here); then, once added, `helm plugin install` pulling latest `helm-diff` against this workflow's pinned Helm 3.16.2 failed to load ("unknown field platformHooks" in the plugin's manifest - a schema field newer Helm expects that 3.16.2 doesn't know). Rather than hunt for an older helm-diff release compatible with Helm 3.16.2, matched CI to the exact combination already proven locally all session (`helm version` / `helm plugin list`): Helm v4.2.4, helm-diff v3.15.11, `--verify=false` for the same reason already documented locally.
- `external-secrets`'s Helm release had been stuck at `STATUS: failed`, revision 1, since the very first webhook-endpoints race at the start of this whole session - the identical issue found and fixed for `cluster-autoscaler` at the same time, but only `cluster-autoscaler` actually got retried back then; `external-secrets` was found in the same broken state and never circled back to. Left unaddressed, it silently blocked the backend release much later (`ClusterSecretStore`/`ExternalSecret` validation failing with `service "external-secrets-webhook" not found`) and was very likely why `external-secrets-cert-controller` had been failing its own readiness probe for hours - it can't complete its own reconciliation without the Service that release never created. Fixed with the same `helmfile sync` used for cluster-autoscaler; also bumped this release's `wait: true` timeout to 600s after the very next sync attempt still failed on "Progress deadline exceeded" even though the Deployment was confirmed healthy moments later - its own reconcile cycle (`--crd-requeue-interval=5m`) sits right at the 300s default with no margin.
- `deploy-backend.yml` swaps AWS credentials from `terraform-ci` to the narrower `platform-ci` (EKS access only) partway through, for the steps that touch the cluster - but never swapped back before "Publish it for the frontend to read," which needs `terraform-ci`'s permissions (reads Terraform state for the SSM parameter name, then writes to SSM). Hit live as a 403 on `s3:ListBucket`/`PutObject` and `ssm:PutParameter` under `assumed-role/conduit-dev-platform-ci` - fixed by re-assuming `terraform-ci` immediately before that step.
- The backend's k6 smoke test returned a 100% error rate against a freshly-"deployed" backend - both pods were stuck in `ImagePullBackOff`, pulling `conduit-dev-backend:latest`, a tag that's never been pushed to ECR (only `sha-<commit>` tags have). `helmfile apply` had reported success on every prior deploy because the image reference had, in fact, never once actually changed: `deploy-backend.yml` passed the tag via `helmfile apply --state-values-set imageTag=<git-sha>`, and `values.yaml.gotmpl` read it back as `{{ .Values.imageTag }}` - but Helmfile state values (what `.gotmpl` value files see as `.Values`) render *before* CLI overrides are merged in ([helmfile/helmfile#700](https://github.com/helmfile/helmfile/issues/700)), so that flag was never actually visible to the template, on any deploy, ever. Confirmed directly: `helmfile write-values --state-values-set imageTag=...` showed no `tag:` key in the resolved values at all. The chart's own bundled default (`image.tag: "latest"`) silently won every time instead. Fixed by switching to `helmfile apply --set image.tag=<git-sha>` - applied directly to the final Helm values, bypassing the gotmpl layer `--state-values-set` can't reach in time - and removed the now-dead `{{- if .Values.imageTag }}` conditional and the unused `imageTag: ""` default it depended on.
- Regression in the fix directly above: `deploy-backend.yml`'s `helmfile apply` had never been scoped with `-l` to the `conduit-backend` release specifically, despite that being its only documented job - harmless as long as nothing passed a CLI override, but `--set` applies to *every* release helmfile processes, not just the one it's meant for. The very first real run of the `--set image.tag=<git-sha>` fix also overrode `aws-load-balancer-controller`'s own, unrelated `image.tag` field (defaults to `v3.5.0`) to that same backend git-SHA tag, which obviously doesn't exist in that image's own registry. Live impact: one LB controller replica stuck in `ImagePullBackOff` and that release's own upgrade reported failed ("Updated: 1/2, context deadline exceeded") - the 2 original healthy replicas kept serving throughout (standard rolling-update behavior), so ingress traffic was not actually interrupted, but the release was left in a bad state until a corrective sync restored it. Fixed by adding `-l name=conduit-backend` to the apply command.
- The first backend pod to ever actually pull its correct image (both fixes above) immediately crashed on startup: `net/url: invalid userinfo`, then a nil-pointer panic inside gorm's `AutoMigrate` once it tried to use a `nil` `*DB`. The `ExternalSecret` template concatenated the RDS master password straight into `DATABASE_URL`'s userinfo section with no escaping - AWS Secrets Manager's random-password generator excludes `/`, `@`, `"`, `\` by default, not `[` or `]`, and the live generated password happened to contain one. Never actually safe, just lucky until this specific password. Fixed by piping both username and password through External Secrets Operator's `urlquery` function (Sprig's `url.QueryEscape` - ESO v2's template engine supports the full Sprig function set).

## Deliberately not done (next steps, not oversights)

- OCI Helm chart registry publishing (charts currently referenced by local path/upstream repo, not versioned artifacts in ECR)
- A spot-instance mix for EKS nodes (cost optimization, not attempted here)
- Kyverno/OPA policy enforcement in-cluster
- AWS WAF in front of either ALB
- A custom domain, ACM certificate, and HTTPS for either tier
- Actually executing the backup/restore runbook against live infrastructure (written, not drilled)
- The forked frontend's own `Security Tests` (XSS sanitization) and `Playwright Tests` (error-handling flows) currently fail - both are bugs in the app's own logic, not this project's infra/CI/CD, and the task brief is explicit that the app itself isn't evaluated. Left as-is rather than debugging Angular component/sanitization internals, which is a different skill area than everything else this repo covers.
- A live pod/node-kill self-healing demonstration
- Automatic ratcheting of the k6 performance baseline (currently a deliberate, human-reviewed commit - see `scripts/k6/compare-baseline.sh`)
- A GitHub App (installation tokens) instead of a long-lived fine-grained PAT for cross-repo `repository_dispatch`
- cert-manager for the LB controller's webhook cert - fixed the immediate bug with `keepTLSSecret: true` instead (reuse the self-signed cert indefinitely rather than regenerating it every apply). Fine for a 10-year-valid cert on a dev cluster that won't run anywhere near that long; a real production cluster would want cert-manager's active renewal/observability instead of a cert that's generated once and never touched again.
